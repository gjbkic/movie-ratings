# 第③段階：取得共有化と到達不能コードの整理

基準はPR #6/#7、検証済みUI、PR #8の同期保護を合わせたd3b8d87。main・既存PR・保存形式・実データは変更しない。第④〜⑦段階は未実施。

## 変更

- app-catalog.jsに同一originのtmdb-metadata.json取得を集約。app-enhancements.jsの監督/ポスター、検索候補、絞込、app-cast-resolver.js、app-people.jsの5消費箇所が同じ取得Promiseを使う。
- 起動時5リクエストを1へ削減。手動の「データを再読み込み」は新しい取得を開始する。実行中の重複要求は共有し、失敗後の遅い消費側が連続再試行しない。手動再試行は可能。
- 返す値は別コピー。既存実装で独立JSONを受け取っていた消費側同士の参照共有・書き換え波及を避ける。セッション内に最後の取得だけを保持し、localStorageや映画バックアップへ新しいキャッシュを書かない。既存の自動メタデータ適用・手動データ優先ルールは維持する。
- 起動時のIDB復元より先に自動ポスター/監督情報を適用すると、その後のstate置換で表示用メタデータが消える既存の競争も確認。新旧コードで同じ架空カタログのテストが失敗した。applyCatalog直前にStorageReadyを待ち、復元停止時には適用しない。
- PR #8で同期入口を統一したため到達不能になったv23のmakeLivePayload、liveFilmRow、remoteSha、syncHeaders、utf8Base64、setLastSync、syncBusyと専用定数を除去。各関数は同じIIFE内に閉じ、外部公開されず、呼出し元は削除対象内だけ。現在のv63ペイロード生成や保存処理は残す。
