# LB同期の待機時間：計測と次の限定実装

2026-10-19、基準1d466b1。実アカウントへの通信・Actions起動・本番保存は行っていない。

## コード上の経路

app-core.js v69のserverFetchRssはtrigger書込み後、2200msごとにRESULT_PATHを確認し、経過70000msで打ち切る。gh/putTrigger内のfetch自体にこの経路固有の中断期限がないため、70秒は厳密な全体上限ではない。失敗後はbrowserFetchFreshが直接/CORS代理3経路を順番に試す。このfetchにも個別の中断期限がない。

sync-letterboxd-on-push.ymlはGitHub側でRSS取得してコミットする。curlのconnect-timeout15秒/max-time45秒/retry1に加え、外側3試行とsleepがある。ジョブ待機時間もアプリ側で制御できない。ユーザーの約1分がどこで発生したかは端末側の記録なしでは断定できない。

collectReviews、鑑賞履歴、採点保護が順に保存を行う。app-enhancementsの最終sync wrapperはinProgressで同時同期を共有し、finallyで採点を復元している。単純に内部save/renderを外すと、中間保存や保護処理の実行順を変える。

scripts/regression/lb-sync-profile.cjs。架空740作品・ローカルChrome、全通信を既存harnessまたは明示mockで遮断。GitHubトークンはsynthetic-not-a-credentialという架空文字列のみ。実ユーザーのRSSやデータは未使用。診断用で通常allには追加しない。

## 設計判断と次回のSol向け実装範囲

最優先は待機を有限にする。v69の取得に限定したfetchヘルパーでAbortControllerを使い、レスポンス本文読込まで期限を適用し、finallyでタイマーを解放する。Promise.raceだけで裏の取得を残さない。GET/PUT/本文停止をmockで試す。取得失敗は同期成功にしない。期限切れで古いRSSを最新として適用しない。70秒確認の枠と既存フォールバック順をまず維持し、各要求上限と残り全体時間を区別する。POST/PUT期限切れはサーバーで成立している可能性があるため、無条件の再送追加は禁止。既存putTriggerの再試行回数を増やさず、トリガー照合を維持する。

次の限定実装で、即時成功・要求停止・本文停止・エラー・別trigger・保存失敗のテストを作り、letterboxd/letterboxd-reviewと同期関連回帰へ実行範囲を絞る。この契約内の実装はSol中で進められる。

固定2200msを短くするだけではActions待ちの約1分は解消しないため、API要求数を増やす変更は当面行わない。直接取得とActionsを競争させる方式は、遅い取得の追適用・重複Actions・取得元の保証が変わるため採用しない。GitHub resultとRSSの別読込は別端末のtriggerで取り違える可能性があり、将来取り組む場合は同じコミットの組で読む保証が必要。

保存3回/描画2回の統合は第⑥段階へ持ち越す。まず中間状態、例外、未保存手編集を含むテストを固定する。同期前後のスナップショット比較で全フィールドを保持し、最終保存の成功を確認するまで完了表示を出さない設計にする。今回アプリ動作は変更せず、計測と設計のみ。
