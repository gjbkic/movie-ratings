# 実データ移行前の限定レビュー

2026-10-20、基準6463f8c。結論：実データへの接続・移行確定へはまだ進めない。今回アプリコードは変更しない。activated:falseを維持する。

## 重大リスクとコード上の根拠

1. **P1：手動復元以外の入口には点数帯検査がない。** app-core.js:102 movie30ValidStateは配列/辞書の形だけを検査。:131 movie30Candidateはその検査と任意のchecksumを使う。:213付近のlive-state起動取込はValidState後にnormalizeStateする。架空740作品をplanで変換し、現コードから両関数を抽出してNode VMで実行すると、新帯stateを両方とも受け入れた。実ブラウザの起動採用全体や本番での破損を今回再現したわけではない。起動・復旧・別タブ・同期等へ共通の入口判定が必要。

2. **P1：プレビュー種別は採用防止の強制境界ではない。** app-score-preview.jsはtype:fictional-score-preview-onlyとstateを出力する。app-core.js:471 restorePackageはobj.stateを先に取り出し、外側のtypeを検査しない。現在の通常UIではbalanced-v1とlegacy-v23の不一致で拒否するが、新帯UIではこの拒否理由が消える。さらに元から公開済みの旧コードに新ガードはない。markerや外側typeを取り除いたものを、本物の旧データと完全に識別することもできない。新版入口でプレビュー種別を拒否し、旧版とは保存先・同期先を分離する必要がある。「ラベルを付けたから本番に入らない」とは言えない。

3. **P1：変換後だけの比較では旧版の正当な変更を失う。** app-score-policy.jsのconvertScoreで50→54、51→54を実行確認。旧版で50から51に編集されても変換後は同値。変換結果を逆算して元データを復元することもできない。元の固定スナップショットを必ず保持する。

4. **P1：候補の原子保存は移行確定の原子性を提供していない。** app-score-migration-store.jsのcommitはbefore-conversionとcurrentを1トランザクションで保存し、初回以外は不一致を拒否する。ここでcurrentは候補であり、通常アプリの有効stateではない。decodeは構造・policyしか検査せず、正しい変換かまでは検証しない。別DBへの通常stateコピーやlocalStorageの完了印とこの保存を単一トランザクションで確定する仕組みは未実装。stageは呼出側のreadSource/withLegacyLockを信頼し、activated:falseのまま。これをtrueにするだけでは安全にならない。

5. **P1：GitHubの編集元検証と点数帯の検証は別。** app-core.js:5815–5845はimmutable blob SHA、canonicalな送信元、cloudBase/cloudSha、応答喪失時の内容照合を扱う。これは維持すべき保護。ただし:5825のリモート検査はmovie30-live/schema2/ValidStateであり、移行状態・プレビュー種別・ポリシー対応を検査しない。SHAの一致は点数帯が正しい証明にならない。旧live-state.jsonへ新帯を書かない設計が必要。別端末の未送信編集までGitHub HEADから把握することはできない。

既知のlocalStorage即時可視性問題は未解決。読み直しやstorageイベントの観測を移行確定の証明にしない。

## 比較に使う記録（設計案、統合はまだ実装しない）

- B：ユーザーが選んだ変換前の固定JSON全文と、その時点のカタログ。作品oldScoreを参照するため、JSONだけで同じ変換を再現できるとは限らない。
- C0：同じ変換規則・カタログでBから生成した未編集候補。
- L：後日取得した旧版JSON。出力日時は参考情報に留め、常に最新とは呼ばない。
- N：新版で編集を始めた場合の現在state。開始前はC0。

最初に旧形式のままB→Lを比較し、採点・星・レビュー・未知フィールド・削除を検出する。次にC0→Nを比較する。Lを変換した結果だけでBとの差を消さない。双方に変更があれば選択対象として表示する。片側のみの変更も、当面は提案として表示し自動確定しない。

順位は作品ごとの単純な値ではなく、点数変更と順位グループの並びを一緒に比較する。圧縮で統合される複数の旧帯をひとまとまりに扱い、後日の点数移動や削除で他作品を消さない。レビュー本文は分割・連結しない。鑑賞履歴は安定IDが同じで内容が違えば競合、IDのない履歴を推測で同一視しない。欠落/null/0/空文字、未知フィールドも区別し、削除を無条件で追加に戻さない。

## 移行確定へ進むための条件

候補と確定stateの意味を明確に分離する。既存stateの内部形式を一括変更せず、必要な由来情報を独立した管理レコードに持たせる案を検討するが、具体的な新形式は今回決定しない。元JSON、カタログ/変換規則の識別、候補の全文照合、ユーザーが確認した対象を結び付ける必要がある。

将来の確定先を同一DBにまとめて原子的に扱うか、別DBへコピーして有効参照を安全に切り替えるかは追加設計が必要。どちらでも、途中終了・読戻し不能・容量不足時に「旧版は保持、候補は未確定」が成立しなければならない。再起動時は候補の存在だけで有効化しない。完了印とデータが不一致なら停止する。旧版が後から編集される場合に、その記録をどう再取り込みするかを確定前に提示する。

GitHubはrepo/branch/path、取得したSHA、編集元内容、点数帯、移行状態が一致して初めて送信対象とする設計が必要。競合・応答不明時に最新SHAへ差し替えて再PUTしない。旧同期先を残し、新同期先を用意する案が推奨だが、作成・配信・実データ投入は今回承認対象外。

## 最小の次Sol工程

**入口判定の純粋関数と架空テストのみを先に作る。** 入力の外側種別、state policy、経路（通常復元/プレビュー/起動候補/同期）、実行側policyから「受理可能/拒否/明示移行が必要」を返す。新保存形式、書込み、自動変換、自動統合は含めない。旧markerなしの正常データは、従来版の入口で後方互換を保つ。プレビュー候補は通常復元・同期で拒否。取り外されたmarkerを完全検出できない限界も記録する。

必要な失敗テスト：同policyのプレビュー候補、異policy、未知/null marker、外側を無視したstate抽出、起動経路、同期経路、旧markerなし正常state。拒否された入力が現在state・保存・送信へ到達しないことは、後の接続テストで別途保証する。既存復元テスト1件だけを入口全体の安全性として扱わない。

その次にB/C0/L/Nの差分を読み取り専用で作る。圧縮で点数差が消える例、同じレビューの双方編集、順位移動と削除、後日追加、0/null/欠落を最小fixtureにする。自動採用ポリシーは決めない。

## ユーザー判断が必要になる時点

実際の切替前に、(A)旧版編集をいったん止め最新JSONを固定して切替（推奨・工程が少ない）、(B)並行編集を続け、後日差分を毎回明示確認して取り込む（競合画面が必要）のどちらで運用するか確認する。今のプレビュー開発を止めて質問する必要はない。保存先/同期先、戻し方、移行前バックアップの取得を具体化してから判断材料を提示する。
