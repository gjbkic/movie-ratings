## 設計レビューの結論

採用: Web Locksで起動時の候補確認・保存・別タブ反映を同じoriginの排他区間に置く。localStorageとIndexedDBを合わせた保存の直列化が必要なため、IndexedDB内だけの比較交換案は採用しなかった。LS先行保存、IDB代替、どちらかだけ成功した場合の保存成功という既存契約を維持する。

旧コードはstorageイベントの更新日時だけでメモリ上の状態全体を置換し、saveはLSへ即座に書いた後、タブ固有の非同期キューでIDBへ保存していた。受信拒否だけでは古いタブからの上書きを防げない。チェックサムは完全性・編集意図の証明にならない。

- 保存呼出時の状態を固定し、ロック取得後、LSとIDBの生の保存内容を、そのタブが最後に確認した両方の内容と比較する。一方でも違えば書き込まない。未配送のstorageイベントや同時保存でもこの比較を通す。
- 保存中もロックを保持し、IDBトランザクションの完了まで待つ。確定した書込みごとに基準を進める。確定前に自動保存済みと表示しない。
- IDBのcurrentと同じトランザクションで補助レコード multitab-commit を更新する。変更前のペイロード、確定JSON、LSの状態を記録し、通知の由来を確認する。状態本体のupdatedAt・storageIntegrityだけを除き、キー順を正規化して比較する。null、0、キー欠落、配列順、未知フィールドは比較から除外しない。
- BroadcastChannelは確定後の通知に使う。IDBだけ／LSだけ成功した更新も通知できる。storage・focus・visibilitychangeは保存先を再確認する契機とし、イベントのnewValueを直接反映しない。
- 完全な直後の更新で、現在タブが未編集かつ保存待ちでない場合にだけ反映する。通知の由来・基準が一致しない、未保存編集や保存待ちがある場合は自動統合しない。
- 競合タブの保存と外向き同期を停止。現在タブと両保存先の候補を、current/previousとは別の multitab-conflicts へ退避して通知する。他方の正常なタブの確定内容を消さない。
- 退避候補は最大12件・JSON文字列合計1200万コード単位。上限・容量不足時に古い候補を削除せず、失敗を明示し、メモリ上の両候補をJSONとしてダウンロードできる。起動時にも退避記録の存在を通知する。
- beforeunloadで古いタブの状態を無条件保存する処理は廃止。未保存／保存中／競合時はブラウザの離脱警告を要求する。非同期保存が終わる前の強制終了を保存成功とは扱わない。
- Web Locks非対応時は既存データを読み込むが、競合を防げない書込みは停止してバックアップを案内する。

## 変更範囲・互換性

app-core.jsの保存・復元・別タブ処理、競合通知、同期入口の保存中／競合ガードだけを変更。ランキング、ドラッグ、検索、復旧参照のロジックは変更しない。

映画stateのスキーマ、version:23、localStorageキー、current/previousの形式、通常JSONバックアップ、IndexedDBのDBバージョンとobject storeは変更しない。保存形式の移行はない。既存object storeに上記2つの補助レコードを追加するため、追加の保存領域は使用する。コミット記録は1件を更新し、競合記録は上限を設ける。補助レコードは通常の作品JSONやGitHub同期へ含めない。

競合ダウンロードは通常の復元JSONとは別の候補一覧。各candidates[].jsonが従来のstate JSONであり、どちらを採用するかを人が確認するためのもの。候補一覧を無条件に復元したり、退避候補を自動適用したりしない。競合タブの停止解除・候補統合UIは今回追加していない。まずJSONを保存し、候補を比較・統合してから通常の復元経路を使う。退避記録は自動削除しない。

live-state.json、復旧JSON、バックアップ、実作品データ、main、公開設定は変更していない。GitHub経由の別端末競合を解決する変更ではない。

## 2026-10-15: P1の2点の修正

最初にP1の正常要件2件を追加し、365a7eaで両方失敗することを確認してコミットした。

停止後のsaveも同じWeb Lock内で現在の編集・両保存先を再退避する。通常保存としての成功は返さず、保存停止の表示を維持する。退避失敗時にもメモリ上の候補を保持し、JSON出力には過去候補と現在の最新編集を含める。未解決退避のある起動時は保存停止を維持し、再起動だけで解決済みにはしない。

新しいapp-conflict-recovery.jsは復帰専用。通常JSON復元のメタデータ優先規則を使わず、候補の差分を再帰比較し、異なる全項目に左／右の選択を要求する。配列は順番や対応を壊さないため全体を選択する。null、0、キー欠落、未知フィールドを区別する。レビューなど同一項目の値を両方本文へ自動連結はしない。片方を明示採用しても他方は退避記録に保持する。別々の項目では左のレビューと右のジャンル・順位などを組み合わせられる。

比較時の両保存先と現在タブの内容を保存直前に再確認する。未選択・順位重複・点数と順位の不整合・比較後の変更があれば停止する。両候補の永続退避成功後のみ選択結果を書き込み、成功した保存先を読戻して確認する。解決記録の確定後に停止を解除する。復帰中に追加編集があれば画面の状態を選択結果で置換せず、追加編集を再退避して停止を維持する。両保存先失敗時も停止を解除しない。

復帰によるstateのスキーマ移行はない。DBバージョンとobject storeは維持。補助レコードにactive／resolvedJsonを追加し、解決前の候補は削除しない。新モジュールとcoreの読込URLを更新して旧キャッシュ混在を避ける。本番への反映は未実施。

### 復帰操作

1. 競合したら、まず「競合した両候補をJSON保存」でバックアップを端末へ保存する。退避失敗の警告時は、アプリを閉じる前に保存ファイルが読めることを確認する。
2. 「退避候補を比較して復帰」を開き、左と右の候補を選び「候補を比較」。各差分を展開し、内容を読んで全項目を選ぶ。候補番号と保存元を確認する。
3. 点数を別候補から採用する場合、対応する順位配列や作品一覧も整合する組合せにする。不整合なら保存されない。配列単位では一方を明示採用するため、必要な追加作品や鑑賞履歴が選択結果にあることも確認する。
4. 「選択内容を退避・保存して復帰」を押して確認する。保存確認済みの表示を待つ。途中で編集や他タブ更新があれば再比較する。
5. 再読み込みし、採用したレビュー・点数・順位・追加作品などを確認する。元候補は「データ」画面の「競合の退避記録を確認」から再比較・JSON出力できる。必要なら他の候補も同じ手順で統合する。
