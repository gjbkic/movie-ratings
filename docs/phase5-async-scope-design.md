# 非同期ポスター更新の計測と限定設計

基準ee1c06e。poster-async-profile.cjsは配信するapp-enhancements.jsのコピーへ一意なアンカーでカウンターを挿入する。ファイル本体は変更しない。架空740作品、外部通信遮断、Chromeモバイル相当。各操作後300msの窓でv89/v90の実行順と要求回数を観測し、全state不変を確認した。結果はtest-results/poster-async-profile.json。

|操作|v89実行|v90要求|v90実行|
|---|---:|---:|---:|
|ランキング描画|1|2|1|
|検索|2|3|2|
|検索解除|1|2|1|
|詳細表示|2|2|2|
|詳細を連続切替|2|2|2|
|詳細整形のみ|0|0|0|
|待機|0|0|0|

呼出し数の計測であり所要時間の改善率ではない。300ms外の遅延処理やiPhoneは未検証。v89の実作品固有の補正対象は架空fixtureに含まれないため、その補正内容の実機確認を意味しない。v89とv90の実行順は現状を維持する。

## 判断

既存の各pendingフラグは機能している。通常ランキングの要求2回を実行1回にまとめており、追加の共通RAF管理は不要。検索の2回目は自身の装飾でchildList通知が発生することと整合するが、通知だけで外部更新と自分の変更を区別できないため、2回目を一律に捨てない。

v90の詳細監視からの更新でもrefreshPostersが一覧・検索結果・詳細をすべて走査する。最初の限定変更は更新対象を分けること。v89の公式ポスター補正、v99の位置合わせ、120ms詳細整形、画像取得側は触らない。

## 次回の限定実装（Sol中で進行可能）

1. refreshPosters末尾の詳細用処理だけをrefreshDetailPosterへ同じ順序で抽出し、全体更新の末尾から呼ぶ。
2. v90のscheduleRefreshへ詳細専用要求を追加。既存の引数なし呼出し・公開refresh・一覧描画・一覧監視は従来の全体要求のまま。詳細パネル監視だけ引数を明示して詳細専用要求とする。MutationObserverの引数をscopeとして誤認しないよう、専用コールバックで包む。
3. 同一フレーム内に全体要求が一度でも来たら全体を優先。予約実行直前にpendingと対象をリセットし、実行中や実行後の変更通知は次フレームへ予約できるようにする。
4. 実行時のselectedIdと現在のDOMを使い、予約時の作品やノードを保持しない。切替済み作品への誤反映を防ぐ既存条件を維持する。
5. 詳細専用経路では一覧装飾を呼ばない。全体経路は従来どおりv84→結果装飾→ポスター差替え→詳細。別モジュールの予約と統合しない。

先に検証する契約：詳細だけの通知で一覧走査が増えない／詳細→全体と全体→詳細の要求はともに全体優先／予約後の作品切替／後着メタデータの全体refresh／詳細の注釈追加で次フレームが必要でも収束／検索候補と未確定カードの画像維持／ドラッグ中の操作と保存データ不変。既存poster-refresh、pending-posters、detail-unified、search-dragを活用し、診断計測を前後で比較する。DOM監視の解除、共通イベントバス、描画の全面置換はこの実装に含めない。

今回は計測と設計のみ。アプリ動作・main・本番・実データに変更なし。計測スクリプト成功、全state不変。新しい通常回帰の追加や全32スイートの再実行は行っていない。
