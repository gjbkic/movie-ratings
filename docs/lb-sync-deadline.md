# LB同期：停止した通信を中断する

基準a97075a。v69の手動LB同期経路に限定し、GitHubのGET/PUT、直接RSS、代理取得、公開RSS読込をapp-lb-transport.jsへ渡す。1要求15秒、本文読込までAbortControllerの対象にし、finallyでタイマーを解放する。別機能のfetch、保存形式・データ・同期順序・Actionsは変更しない。PUTタイムアウトはサーバー側で成立している可能性があるため再送せず、既存の直接取得へ進む。その他の既存再試行回数は増やさない。

サーバー結果ポーリングは2200ms間隔/70秒を維持し、残り時間以内に要求を中断する。70秒はtrigger書込後の結果確認枠であり、LB同期全体の上限ではない。トリガー準備、RSS本文取得、フォールバックは別途かかる。ActionsのキューやRSS側の応答が遅ければ依然1分以上になり得る。今回の成果は正常時の速度向上ではなく、停止した通信による無期限待機の防止。

直接取得/代理取得のいずれかがタイムアウトし、後続の新鮮な取得も全失敗した場合、公開済みRSSを最新として適用しない。従来の公開RSSフォールバックは、タイムアウトのない従来エラー時に限って維持。GETが即時成功しても本文が止まるケースを期限対象とする。

## 検証

- lb-transportの5件：正常本文/HTTP409/引数保持、GET停止、PUT停止・再送なし、本文停止、ネットワーク例外。すべて成功。
- lb-sync-deadlineの隔離架空740作品3件：4取得先停止でfalse・失敗通知・点数順位レビュー不変、PUT停止後に再送せず直接取得、別triggerを採用せず次の正しい結果を待つ。すべて成功。テストでは期限だけ30msへ短縮し、アプリの本番設定は15秒。
- 最初のall-stalledを実ユーザー名経路に変更すると、古い公開RSSへ落ちtrueになる不具合を確認。抑止後3件成功。
- 通常runnerへ両スイート登録、全30スイートを実行。最終結果は後続記録に追記。

全回帰のdata-contractでIDB-onlyプロセス再起動テストが、初回保存時「保存停止 · タブ間保存の確認に失敗しました」で失敗。単独でも再現。test-results/lb-baselineへ変更前a97075aのcoreを置き、同じ隔離テストで同じ失敗を確認。通信変更前でも再現するため今回の変更による回帰とは断定できない。原因は未確定。診断のため同テストのアサーションに保存結果を追加した。安全性に関わるため無視して公開せず、別途切り分ける。保存停止ガードは緩めない。
