ただし追加のリモート競合レビューで未解決のデータ損失経路を再現した。GitHub PUTが503で失敗した後、別端末相当がリモートをrevision A→Bへ更新すると、次の自動再試行はBのSHAをGETしてそのまま古いローカル候補をPUTできてしまう。PUT自身は409にならず、相手のレビューを上書きする。これは同一ブラウザMULTITABのロックとは別問題。従来の手動同期にも同じ構造があり、再試行の復活によって無視できなくなった。

## Astra中で確認・設計すること

- 再試行時にSHAが変わった場合、原候補と新リモート候補を保全し、勝手に上書きせず停止する設計。503/通信断で最初のPUTだけ成功していた場合も区別する。
- 旧版が失敗前に書いた既存の「同期済み」指紋の扱い。日時だけで信用したり、全件を勝手に再送したりしない。映画stateの移行を伴わない方法を検討する。
- 長いPUTの間に編集し、既存の自動タイマーがbusyで見送られた場合の未同期表示と後続送信。現在は送信した版だけを指紋確定するが、後続保存/手動同期が必要な場合がある。

## Astraレビュー後の修正（2026-10-16）

上記は92120ad時点の停止記録。続行では以下を実装した。映画state、JSONスキーマ、DB、既存保存キーの形式は変更しない。

- 起動時に復元済みの同期対象stateをセッション内の編集元として保持。GitHub本文がその編集元と完全一致するか、同セッションで確認済みのSHAである場合にだけPUTする。オブジェクトキー順のみ正規化し、配列順、0、null、キー不在、未知のstateフィールドを同一視しない。日時と旧指紋は祖先確認に使わない。
- SHAが変わり内容も異なる場合、読み込めない本文、編集元が不明な場合は同期停止。現在の端末JSON（停止後の追加編集を含む）と確認時点のリモート原文JSONを個別に出力できる。同期停止はローカルの編集・保存の停止とは別。
- PUTの応答だけ失った場合、再読込したリモートstateが実際に送った版と完全一致すれば送信済みと認識し、二重PUTしない。異なれば上書きしない。
- 送信中の追加編集は未同期と表示。既存の自動タイマーがbusyで終了していても、成功後に再スケジュールする。自動同期がOFFなら後続自動送信しない。
- トークン設定ボタンが古いsyncToGithubを直接呼ぶ迂回経路も、失敗テスト（PUT 1回で相手レビューを上書き）を確認して同じ保護へ委譲した。
- Contents APIのencoding:noneは同じSHAのGit Blob APIで取得する。現在の追跡済みlive-stateはサイズ情報だけで2,647,664バイトと確認。実データをテスト入力には使用していない。未知のトップレベルenvelopeメタデータは送信時にも保持。

API根拠: https://docs.github.com/en/rest/repos/contents#get-repository-content / https://docs.github.com/en/rest/git/blobs#get-a-blob 。ファイル本文取得中の他端末変更はPUT時のSHA条件で409となり、次回も元のSHAを勝手に置き換えない。

### 意図的な制約と復帰

共通の編集元がないデータ同士を安全に自動統合する機能は今回追加していない。未同期編集を保存して再起動した場合、GitHub側との差分は正当なローカル編集だけでも同期停止になることがある。これは一方のレビューや順位を推測で採用するより保護を優先する動作。

停止したら端末JSONとGitHub JSONを両方保存し、追加編集後は端末JSONを再出力する。どちらかのJSONを無条件にインポートして復帰しない。比較・統合と双方への反映は別途明示的に確認する必要がある。同期停止状態のリセットだけで送信を強制する操作は提供しない。再読み込み後も内容が一致しなければ停止する。候補の自動永続退避は今回追加していないため、再読み込み前のJSON保存が必要。localStorage/IDBの既存保存はそのまま動作する。

PR #6の同一ブラウザ競合UIとは別機能であり、GitHubの候補をそのまま#6の復帰に流用しない。実機iPhoneで今回のGitHubモック・HTMLファイル起動は未検証。既存v3/v4の実機合格を今回の修正の証拠にはしない。
