# 同時履歴保存の設計レビュー（実装前）

基準758c09e。開始時5時間残36%、週間残26%。停止境界25%に近いため、今回は設計のみ。新しい実装・テストは行っていない。

## 結論

単にsaveのPromiseへthenを付けて履歴を追加する案は採用しない。映画stateのlock解放と履歴更新の間にpeer採用や次のsaveが入り、shadowや履歴の世代がずれる。また失敗時にも現在のwrapperはshadowを進めるため、そのままでは後の成功時に履歴差分が欠ける。

推奨案は、既存の映画保存lock内に履歴確定の内部hookを置く方式。履歴追加・Undo削除は共通履歴lockへ統合するが、取得順序は常にstate lock→history lockとする。history lockからsaveやstate lockを呼ばない。現在の通常UndoはoldSaveを待ってからLS削除しているため、その削除を成功hookへ移す必要がある。別々の箇所で再入lockを取得する実装は避ける。

## 保存の順序と契約

1. save呼出時に映画状態のJSONと保存連番を同期的に固定する。後から変わるstateを待機中に読み直さない。公開saveの引数・Promise契約は維持し、内部保存関数にのみ履歴操作を渡す。
2. state lock内で既存disk照合を行う。拒否された保存は共有履歴を書かない。既存の競合退避を維持する。
3. 直前の確定JSON（movie30LastSavedJson）と今回固定したJSONから履歴差分を生成する。起動時shadowや保存要求時のshadowを正当性の根拠にしない。これにより、失敗した保存要求の変更が後で正常に保存される場合も、差分が欠落しない。異なる保存要求が連続した場合は、直前に成功した状態との差分になる。
4. 履歴変更の意図を、上書きしない一意な退避候補として保存・確認してから映画を書き込む。候補には保存連番だけでなくbefore/afterと履歴操作を保持し、実際に確定したか不明な場合は自動適用しない。退避不能時は映画保存も止めてJSON救出を案内するか、履歴を失っても映画保存を継続するか、実装前に契約を確定する必要がある。前者を安全側の推奨とする。
5. 映画保存成功後、state lockを保持したままhistory lockを取得し、最新LS配列を厳密に読み、履歴ID単位で追加または対象IDだけ削除する。壊れたLSを空配列と解釈して上書きしない。読戻し確認後に候補を完了にする。既存の50件/250000文字制限は現在仕様として維持し、競合による消失と通常の保持上限を区別する。
6. 履歴確認後にpeer通知とsave Promiseの解決を行う。映画保存済み・履歴保存失敗は映画保存失敗とは区別し、Undoで映画状態を巻き戻さない。映画保存のboolean結果を流用してfalseを返すと現行Undoのrollbackが走るため、内部の履歴結果を別途扱う必要がある。退避候補と明示警告を残し、成功toastを出さない。
7. sessionHistoryのafter/epochは確定した保存対象に対応させる。peer採用後のshadow更新hookは維持できるが、永続履歴の生成根拠としては使わない。保存中の追加編集は固定JSONと異なるため、上書き・rollbackしない。

## 次回の限定テスト

- 失敗先行：同一contextの2タブでstate lockを一時保持し、A/Bの異なる編集とsaveを両方開始してから解放。成功側の履歴IDが残り、競合拒否側の差分が正常履歴へ混入せず、その編集は競合候補に残ること。
- 同一タブでsave待機中に追加編集し次のsaveを呼ぶ。各確定状態の差分が重複・欠落せず、再読込後の状態と一致すること。
- Undoと他タブ保存の競合で、対象外の履歴IDが消えず、待機が解消すること。state→historyの順序を強制してdeadlockを検出すること。
- 映画保存失敗、映画成功後の履歴書込失敗、候補退避失敗を別々に検証。映画成功後の履歴失敗を理由に映画をrollbackしないこと。
- 既存history-peer-append / history-peer-generation / history-undo-protection / undo-archive-exportを再実行する。全回帰は固定commitゲートまで保留。

本案は実装可能性を整理したもので、安全性の検証済み保証ではない。特に内部結果と退避失敗時の契約を確定してから失敗先行テスト・実装へ進む。現状を公開可とは判断しない。main・本番・保存形式は変更していない。

## 実装追記

5b0452d以降、履歴の生成は保存成功後、映画state lock内の内部hookで行う。直前に確定したJSONと今回保存した固定JSONから差分を作り、専用history lock下で最新LS配列を読み直して追加する。拒否された映画保存は履歴を書かない。通常Undoが映画を保存するときは自動履歴生成を抑え、対象履歴の削除だけをhistory lock内で最新配列に適用する。履歴書込の失敗時は映画保存済みという結果を維持し、別の警告を表示する。

失敗先行の実2タブテストは修正後成功。履歴容量不足を注入しても映画保存結果がtrueで再読込後の変更が残り、履歴失敗警告が出るテストも成功。peer採用後の履歴保持テスト成功。通常Undoの既存9件は一括時8件成功・1件はChrome起動待機タイムアウトだったが、その1件だけ再実行して成功。退避JSON2件成功。全回帰・最終main統合・実機検証は未実施。履歴失敗時の差分候補を独立して永続退避する仕組みは未実装であり、映画状態の保存とJSON書出しから復元する必要がある。この点を公開可否レビューで明示する。
